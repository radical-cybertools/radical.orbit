ORBIT — why it looks the way it does

design decisions · project grounding · pain points
RADICAL group call  ·  July 15, 2026  ·  Andre Merzky
Four projects pull on the same framework —
this is what that did to the design.

ORBIT in one slide

  • Star: one broker hub, every participant dials out — no inbound port at any site, no facility deployment
  • One symmetric msgpack envelope (request/response · events · topology · control), routed by src/dst, correlated by corr_id
  • State: broker rewrite + ticket backlog merged to devel (PRs #64–#96) · ~900 unit tests · CI-gated (3.10–3.12)

Where ORBIT sits — RCT integration

  ROSE        learn      sim + surrogate training + model selection loops
  AsyncFlow   compose    async workflows, dependencies, campaigns
  RHAPSODY    execute    ComputeTask + AITask in one allocation (Dragon)
  ORBIT       connect    HPC resources ⇄ one workflow / campaign
  • RHAPSODY — both directions: ORBIT's rhapsody plugin runs tasks on the endpoint; RHAPSODY's OrbitExecutionBackend uses ORBIT as its execution transport
  • ROSE — ROSE-aaS: the active-learning loop as a broker-reachable service (SURGE races in the m3dc1 / heat recipes)
  • RADICAL Pilot — the lucid plugin wraps pilot/task submission for the LUCID pipeline
  • Makeflow — xGFabric routes Makeflow task graphs off WorkQueue onto ORBIT endpoints

Design decisions — and who forced them

decisionwhyforced by
outbound-only star three sites, zero inbound firewall exceptions xGFabric
broker hosts plugins facility APIs (IRI/SFAPI) need no HPC-side process at all AmSC
3-thread endpoint, transport-only liveness slow plugin init (Dragon ~minutes) must not read as death RHAPSODY
msgpack + frame cap + size-aware batching 10k-task submissions vs bounded frames RHAPSODY
BatchSystem abstraction, normalized states SLURM and PBSPro disagree on everything all facilities
tunnel modes none / forward / reverse each site blocks a different SSH direction Perlmutter · Aurora · Odo
bearer-token ingress gate (interim) prepared for multi-tenancy and mTLS security AmSC security
Pattern: every structural feature traces to a concrete project requirement — nothing speculative survived the rewrite.

  • Drove: IRI plugins (iri_connect / per-endpoint instances), the direct-SFAPI launch path, tunneled child endpoints, the stellar-ai recipes as the packaging format

  • Pain: the NERSC IRI facade broke under us (slide 10) — and broker deployment is an adoption hurdle (slide 11)

project grounding · 4/4

ATOMIC — an iterative campaign as the consumer

  • Needs: the ATOMIC Workflow Manager runs a temperature-ramp loop — MD sim → label → train classifier → next temperature — driven from a user-facing tool (OVITO integration)
  • The shape of the demand:
    • long-lived iterative campaigns, not single jobs
    • launched by scientists who will never deploy a service — the embedded-broker argument again (slide 11)
    • a community portal drawing on dynamically contributed community resources
    • train + simulate concurrently → RHAPSODY over ORBIT
  • Status: requirements/WFM-architecture stage — ORBIT is the planned connect layer, so ATOMIC's requirements doc is a design input now, cheap to accommodate, expensive to retrofit
pain point · 1/3

Every facility blocks a different direction

sitepolicywhat we do
Perlmutter compute→login SSH allowed; arbitrary outbound ports OK forward tunnel: child opens ssh -L via login node
Aurora same direction as Perlmutter forward tunnel
Odo compute→login blocked; login→compute allowed reverse tunnel: parent-side watcher spawns ssh -R, rendezvous file on shared FS
OLCF / ALCF egress unverified for non-443 ports to check — decides the transport question (slide 12)
  • Tunnel failures surface as job FAILED with recorded reason — clients bail early instead of polling a dead allocation
  • IRI-launched jobs give no login-node foothold — that inhibits reverse tunnels (ticket open; direct SFAPI does allow it)
pain point · 2/3

Facility APIs are moving targets

  • NERSC IRI facade broken server-side since ~June 17: all /compute/* → 404 wrapping "Unable to get sfapi data: 500" — ticket open with operators
  • SFAPI single-job status route is blind for finished jobs — we poll via the LIST route instead (second ticket open)
  • Workaround shipped: direct-SFAPI launch path, validated end-to-end on Perlmutter — PR #102 (feature/sfapi), pending merge
  • Design lesson: never depend on a single launch path — IRI, direct SFAPI, and direct scheduler (psij) stay interchangeable per resource; tokens live in process memory only, so swapping paths never touches disk
pain point · 3/3

Broker deployment is challenging for end users

  • Today a user needs: a public host + TLS cert + token distribution to every participant — before hello-world runs
  • That is a significant adoption blocker reported from AmSC uptake
  • Root cause — the broker implements two roles:
    • smart edge: plugin host, session owner, topology view
    • dumb middle: route by src/dst, correlate, fan out events
  • The smart half doesn't need a public IP at all — only the dumb half does → next slide
design direction — for discussion

Embedded broker + a dumb shared middle

  • Embed the smart half in the client — mostly packaging: the broker is already "just a participant" hosting plugins
  • The middle becomes immediately multi-tenant once envelope bodies are E2E-encrypted (key shared like today's token): zero trust in the relay → one instance serves everyone → deployment burden reduced
  • Two candidate middles — current analysis: relay-first
    • dumb WSS relay: keeps envelope, framing, transport-level liveness intact; works wherever today's broker works — pubsub instead forces app-level heartbeats + reinventing suspect/lost, and raw Redis on 6379 is exactly what strict egress filters catch
    • managed pubsub earns its rewrite only if replay / persistence becomes a requirement — then Redis Streams, not plain pub/sub
    • relay-first also decouples the steps: embed plugins in the client now (cheap), swap the transport later, if ever (expensive)
  • Deciding datum: OLCF/ALCF egress — Perlmutter verified open; if OLCF is 443/proxy-only, the relay wins outright
  • Open: broker lifetime = client lifetime; multi-client endpoint sharing; where the Explorer lives
