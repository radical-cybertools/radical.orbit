# Plan: #6 / #16 / #21 — ROSE integration track

Issues (one plan — they are strictly sequential slices of one feature):
- #6  ROSE integration prep: control-plane request shapes (stub)
- #16 ROSE plugin skeleton (endpoint wiring; no orchestration semantics)
- #21 ROSE orchestration scaffolding: state machine + request validation

Status check (2026-08-25): **none started**. No `plugin_rose.py`, no ROSE
tests, no request-shape stubs. What DOES exist:
`examples/example_rose.py` — a *consumer* demo importing the external ROSE
library (`rose.al.active_learner.SequentialActiveLearner`) and driving it
over the existing rhapsody/ddict plugins. ROADMAP.md still schedules the
ROSE plugin for Month 5.

## Scope question to settle first (blocks all three)

`example_rose.py` demonstrates that ROSE already runs *over* ORBIT as a
client library — no plugin needed for the compute path. The remaining
plugin-shaped value is the **control plane**: submitting/monitoring an
active-learning campaign from a thin client (or the Explorer) while the
ROSE loop runs *at* the endpoint. Before implementing, confirm with the
ROSE side (Q1 issue text predates the star flip and the rhapsody plugin)
that this is still wanted. If ROSE-as-consumer-library is deemed
sufficient, close all three with `example_rose.py` +
docs as the reference. The plan below assumes the plugin is wanted.

## #6 — control-plane request shapes (stub)

- A `rose_shapes.py` (or section in the plugin module) defining Pydantic
  models for the campaign control plane:
  `CampaignSpec` (learner type, simulation task template, training task
  template, stop criterion, max iterations, resource hints),
  `CampaignStatus` (state, iteration, tasks in flight, metric history),
  plus request/response models for submit/status/cancel.
- Round-trip + validation-error unit tests; no behavior.
- Deliverable is reviewable shapes the ROSE team can sign off on — keep it
  one small PR that #16 then consumes.

## #16 — plugin skeleton (wiring, no semantics)

- `plugin_rose.py` mirroring the rhapsody plugin structure:
  `PluginRose(Plugin)` + `RoseSession(PluginSession)` + `RoseClient`;
  namespace `rose`; `is_enabled` gates on the `rose` package being
  importable (endpoint-side only, like globus gates on globus-sdk).
- Routes: `register_session`, `submit_campaign` (validates via #6 shapes,
  stores, returns id — stub executes nothing), `get_campaign`,
  `list_campaigns`, `cancel_campaign` (state flip only).
- Notification topic `campaign_status` (emit on the stub transitions).
- E2E-forwarding test via the existing in-process harness
  (test_runtime.py `_RunningBroker` pattern): client → broker → endpoint →
  stub handler → back; minimal per the issue.

## #21 — state machine + validation

- Campaign state machine:
  `NEW → VALIDATED → RUNNING → (iterating: SIMULATE ⇄ TRAIN → EVALUATE) →
  {CONVERGED | EXHAUSTED | FAILED | CANCELLED}` — implemented as an explicit
  table (allowed transitions dict + guard callables), not ad-hoc ifs, so
  the later real orchestration drops into the same skeleton.
- Validation helpers turning #6 shape errors and illegal transitions into
  the shared error envelope (rest_api.rst) with actionable messages.
- The RUNNING internals drive tasks through the **rhapsody client** on the
  same endpoint (the pattern `example_rose.py` proves), initially with a
  no-op learner; real learner integration stays out of scope per the issue.
- Tests: transition table exhaustively (legal + illegal), cancel from every
  non-terminal state, error envelopes, one harness test driving a two-
  iteration no-op campaign to CONVERGED.

## Ordering / effort

#6 (small) → #16 (small-medium) → #21 (medium). All three are
skeleton/scaffolding by design — resist scope creep into real
orchestration. Revisit the scope question first; that one conversation may
close the whole track.
